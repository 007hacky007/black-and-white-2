# Plan 11: Settings, saving and loading in the first land Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Scripted headless runs change a setting in the front end and find it again after a restart, save a game from the first land's pause bar, quit through the game's own path, and load that save from the front end back into the land, with no stop on the way. That is the spec's "change settings, and save and load" (section 2), checked on the first land.

**The boot frontier does not move in this plan.** Today a New Game ends at the creature choice, waiting for the player, and after plan 11 it still does: the save is taken from the pause bar over the live choice, and the load returns to that state. Plan 11 deliberately covers section 2's settings, save and load first, on paths that already run; making the creature choice by script and driving the land past it is plan 12's first task (Ruling 1).

**Architecture:**
- **Scripts that follow the game, not the frame rate.** The engine has no stop left to end on: the land runs and waits for the player. Read counts no longer mark the same moment in two runs (headless rates measured from 41 to 343 Presents a second, and a frame dump slows a run several times over), while the game's scenes run on its own clock. `BW2_INPUT_SCRIPT` gains blocks anchored on the game's movie events (`after open`, `after last`) and on wall time (`after seconds`), and a `quit` verb. Keys are held for a wall-clock time as a precaution, not a measured need: 40 ms presses did work in the land ("Measured" item 4), but a press of a fixed read count (down, then up 4 reads later) lasts from about 12 ms to about 100 ms across the measured frame rates (343 and 41 Presents a second), and a game that samples key state at its own tick could miss the short end. Task 4 checks that one held Escape toggles the pause bar exactly once.
- **Windows facts for the save files.** The save path is the game's own code on win32hle's file calls (directory make, move, delete, find). A small probe program, built on the Mac with mingw-w64 and run on the user's Windows 11 VM, records what Windows answers for the cases the save path meets. Our answers are checked against those facts and fixed where they differ.
- **Three gamefiles boot tests** drive the front end's Options, the pause bar's save dialog and the front end's load dialog by script, and each ends through the game's own quit (`ExitProcess(0)`), so the game writes its profile as it does on Windows.
- **Next layer:** the creature choice (where the boot still ends after this plan) and the first land's tutorial (plan 12), and Bink audio tracks when a scene opens a movie that has one.

**Tech Stack:** C and Objective-C (clang, arm64, macOS 13+), pcrecomp win32hle (vendored, MIT), mingw-w64 (Homebrew; a build tool for the Windows probe only, Ruling 6), the winbench Windows 11 VM, Python 3.14 and pytest.

**Spec:** `docs/superpowers/specs/2026-11-10-bw2-macos-port-design.md` (sections 2, 5.2 Input and Files and saves, 7.3, 7.4, 9, 11). Facts: `docs/research/campaign.md` ("For the next plan"), `input.md`, `frontend.md`.

## Review Focus

- **A script anchor that never fires.** A skipped intro never shows its last frame ("Measured" item 3), so a script that waits for `after last 1798` on that path waits forever and the test only times out. Each firing must print one line naming the anchor and the read, and a test must fail on a missing line with that tail in its message. (Task 1, case `anchor`: a movie of another frame count never fires the block, and nothing after it is pushed; every boot test asserts its full list of anchor lines.)
- **An empty block that arms the next one too early.** A block is armed only when the block before it has fired and pushed all its events, so `after open 1798` with no events holds back the `after seconds` block after it until the intro opens. A rule that armed a block as soon as the events before it were pushed would start the Escape chain during the 23 s land load. (Task 1, case `empty_block`.)
- **A key press shorter than the game samples.** Holds are a precaution (40 ms presses worked in the land, "Measured" item 4), but a read-count press shrinks to about 12 ms at the fastest measured rate. A held key must stay down for its wall-clock time whatever the frame rate, with its up pushed at a later read than its down, never the same one. (Task 1, case `holds`, with a fake clock the test sets to about 1 ms per read and to 1 s per read.)
- **A held key read as a level, not an edge.** If the game polls Escape's state each tick, one 0.5 s hold could toggle the pause bar or cut scene parts more than once and break the press count `SKIP_TO_CHOICE` relies on. (Task 4 Step 3 checks that one held Escape toggles the bar exactly once; if not, presses become short ones with wall-time spacing.)
- **The pause bar's state after the surplus Escapes, and the continue click on a closed bar.** After `N` presses the bar is open or closed depending on how many presses the scenes took. When it is closed, the click at (85, 710) lands on the live creature choice with the game's hand, and could pick or move something; "nothing visible in frames" alone does not rule that out. (Task 4 Step 3: after a continue click on a closed bar, no new import, no file activity and the same frame state.)
- **Fixed wall-time waits on a busy Mac.** The front end appears only after the profile's device reset and the HLSL compile, and `campaign.md` measures 5 to 11 Presents a second on a busy Mac with a reused folder, so a 3 s wait after the profile confirm could click options before the front end takes input, and a 20 s wait for the save could quit before it is written. (Task 3 Step 3 measures when the front end is live and sizes the first wait from it; Task 4 Step 3 sizes the save wait from the measured write time.)
- **Find order.** The game's lists (saves, profiles) come from `FindFirstFileA`. Windows orders names on NTFS by upper case, where `strcasecmp` compares lower case, so names with `_`, `[`, `\`, `]`, `^` or `` ` `` sort differently (the default profile name holds `_`). The order must be NTFS's as the probe measures it, and the sort changes every listing the game makes, game tree and overlays included. (Task 2, check `find_order` in `shims_selftest.c`; Step 6 reruns the New Game boot right after the change.)
- **Saving over a save.** A second autosave or a save into an existing slot moves files onto names that exist and removes folders that may not be empty. `MoveFileA` onto an existing name, `DeleteFileA` of a missing or read-only file, and `RemoveDirectoryA` of a non-empty folder must answer as Windows does, with Windows' error codes. (Task 2, checks `move_onto`, `delete_cases`, `rmdir_cases`.)
- **A resolution change under the script.** After the settings test's reset to 800x600 the client rect shrinks. The script's running point is clamped to the new client size, the game's own cursor may differ, and the front end's buttons move. A click at a 1024x768 place must not be assumed to work at 800x600. (Task 3: the 800x600 places are measured from frames and the test clicks there; the second boot checks the device size from its first frame.)

### Task 1: Script blocks anchored on movies and wall time

**Files:**
- Modify: `runtime/bw2/input/script.c` (blocks, anchors, holds, `quit`), `runtime/bw2/input/input.h` (declarations), `runtime/bw2/video/binkw32.c` (the two movie notices).
- Test: `runtime/bw2/input/input_selftest.c` (group `script_after`), `tests/test_input.py::test_script_after`.

**Interfaces:**
- Produces:
  - Script syntax (in addition to today's lines, which keep their meaning before the first `after`):
    - **Arming.** The first block is armed at the first `bw2_script_at_read(n)` call at which every absolute line before it has been pushed (the first call, if there is none). Each later block is armed at the first call at which the block before it has fired and all of that block's events have been pushed. An empty block is therefore complete the moment it fires, and the block after it is armed at that same call, never earlier. A block's anchor is looked for only from its arming on.
    - **Firing and the anchor read `A`.** A block fires at the first `bw2_script_at_read(n)` call at which its anchor is seen; at that call it prints its anchor line naming `A`. For a movie anchor, `A` is the read counter's value at the movie event (the number of the last read before it, so `A < n`); for a seconds anchor, `A = n`. Inside a block, read numbers are `0` or more and non-decreasing, and event `k` is pushed at the first call, at or after the firing call, whose `n` is at least `A + k`. So an `after open` event `0` comes at the first read after the movie event, and event `5` at read `A + 5`.
    - `after open <frames>`: a movie with `<frames>` frames is opened (`_BinkOpen@8` returns a handle) after the block was armed (an event recorded before the arming call does not count);
    - `after last <frames>`: the same, when that movie's last frame is copied after arming;
    - `after seconds <s>`: the first call whose clock is at least `<s>` wall seconds (decimal, `strtod`, greater than 0 and at most 3600) after the clock at the arming call;
    - `<read> quit`: exit 0 with `[bw2] script: quit at read <n>` (a test switch like `BW2_QUIT_AFTER_READS`).
  - Each anchor that fires prints `[bw2] script: after <anchor words> at read <A>` (for example `[bw2] script: after seconds 0.5 at read 1234`), with `<anchor words>` as written in the script, normalised to single spaces. Anchor lines print in file order, because each block is armed only after the one before it fired.
  - `void bw2_script_movie(int last, uint32_t frames)` in `input.h`: `binkw32.c` calls it with `last = 0` when `_BinkOpen@8` returns a handle and with `last = 1` at the copy that shows a movie's last frame (the moment the `bink last frame` line prints, whether or not `BW2_BINK_LOG` is set). It only records the event and the read counter's value; it pushes and prints nothing.
  - `void bw2_script_set_clock(double (*now)(void))` in `input.h`: the selftest's fake clock, a function returning a value the test sets before each read (the script may read the clock any number of times per call; the value does not step per call); `NULL` restores `CLOCK_MONOTONIC`.
  - The read counter's current value for `bw2_script_movie`: `unsigned long long bw2_dinput_reads(void)` in `dinput8.c`, declared in `input.h`. It advances only through `GetDeviceData` reads (`count_read`), not when `bw2_script_at_read` is called directly.

## Rulings (my calls; the spec leaves them to the builder)

1. **Scope and number.** Plan 6 (input) is done and merged, so this is plan 11. The boot no longer stops: the land runs and waits for the player ("Measured" item 1). Of the spec's "Done means" (section 2), the front end's settings and saving and loading are reachable now, on the first land, with no new layer, so this plan takes them first. It does not move the boot frontier: a New Game still ends at the creature choice waiting for the player, the save is taken over the live choice, and the load returns there. Driving the choice needs its own measured UI (the hand, the creatures' places, what confirms a pick), which no run has measured yet, and a save before the choice already exercises the whole save path. The creature choice (plan 12's first task), the first land's tutorial and the rest of the campaign are plan 12 onwards; the Builder app and packaging come after the campaign plays. Bink audio tracks stay a later-plan stop until a scene opens a movie that has one.
2. **Script anchors on the game's events and wall time, not read counts.** Read counts drift with the frame rate ("Measured" item 2), and the game's scenes run on its own clock. The movie events are the ones the engine already sees (`_BinkOpen@8`, the last frame's copy). Wall time is the game's own time base, and every scene this plan waits through ends in a state that waits for input, so a generous wait is safe. No test-only virtual clock: the game's audio and streaming run on real time, and a fake clock would be a new way to be wrong.
3. **`quit` in the script** ends a run at a moment the script names, as `BW2_QUIT_AFTER_READS` and `BW2_QUIT_AFTER_MOVIE` do, for runs where the game's own quit is not what is being tested. The save and settings tests end through the game's own quit instead, because the game writes its profile there ("Measured" item 8).
4. **Held keys, as a precaution.** No measurement shows a press too short: the presses ignored in "Measured" item 3 came before movie frame 31 to 101, which is timing, and 40 ms presses worked in the land (item 4). But a press of a fixed read count lasts about 12 ms at 343 Presents a second, shorter than a game tick could be. Scripts hold Escape 0.5 s and typed letters 0.2 s, and Task 4 checks that one hold toggles the pause bar exactly once (if the game reads Escape as a level, presses become short ones spaced by wall time); mouse clicks stay as they are (DirectInput's buffered elements carry every press).
5. **Skipping by Escape, then a continue click.** Skipping the scenes saves about 2 minutes a run. Once the choice is live, Escape toggles the pause bar, and nothing the engine sees tells which state the game is in: the land's text is not drawn through `ID3DXFont` ("Measured" item 5), and a hook on the game's own text would mean matching its strings. So the script presses more than enough times and then clicks the pause bar's continue place, which closes the bar if it is open and does nothing on the land if it is not (checked in Task 4: no file activity, no new import and the same choice state after it), and opens the bar with one more press.
6. **mingw-w64 from Homebrew** builds the probe (installed in Task 2; recorded here). It is a development tool on this Mac, like Homebrew's FFmpeg: its compiler is GPL but nothing of it enters the repo, and the probe binary (linked against mingw-w64's permissively licensed runtime) is never committed or shipped. The probe's source is ours, MIT.
7. **The VM.** Used for Win32 facts only; the game cannot be a reference there ("Measured" item 10). Before any change a `vm_snapshot` is taken, and after the work the VM is rolled back to that snapshot, which is then deleted, so `vm_snapshots` lists only `pre-winbench` and `clean` again. This departs on purpose from the workflow's rule "roll back to clean": `clean` dates from 2026-11-08, and `C:\bench` holds about 2,146 entries other work made after it, which a rollback to `clean` would destroy. Rolling back to this plan's own snapshot returns the VM to exactly the state it was found in, which is what the rule protects. Nothing from the VM is committed, only facts. No SafeDisc driver is installed or started there.
8. **Windows wins over win32hle where the probe measured it,** and only there: each difference is fixed with the probe's answer as the check, in a vendored commit for win32hle's code. Cases the probe did not measure keep their present answers.
9. **One saved game per test session.** `saved_game` is a module-scoped fixture: the save test and the load test share one save boot (about 3 minutes), so the suite grows by about 10 minutes, not 15. The load test copies the folder, so the two never share writes.
10. **Coordinates are facts.** Client positions of the game's buttons and rows (measured from frames that were deleted) are committed in tests and docs, like addresses; the frames and the UI's words are not.
