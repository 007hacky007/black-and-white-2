# Plan 9: HLSL from the disc's own D3DX, and the boot to Bink Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The game compiles its HLSL. `D3DXCreateEffect` given HLSL text, `D3DXCompileShader`, `D3DXCompileShaderFromFileA`, `D3DXCreateFragmentLinker` and `D3DXCreateSphere` are answered by Microsoft's own `d3dx9_25.dll` (the April 2005 DirectX redistributable on the user's disc 1), lifted to C like the game. The boot then gets past the profile dialog's tone-mapping effect and runs on to its first Bink call (exit 4, plan 10's layer).

**Architecture:**
- **The compiler is the one the game shipped with.** Disc 1 carries `DIRECTX9/APR200~2.CAB`, which holds the x86 `d3dx9_25.dll` that `white.exe` imports. The pipeline extracts it with macOS's own `/usr/bin/tar` (libarchive), checks its SHA-256, rebases it from `0x400000` (where `white.exe` sits) to `0x08000000` with its relocation table, discovers its functions and lifts it as a fourth module, `d3dx`. Only the catalog (addresses) is committed; the DLL, like `white.exe`, comes from the user's disc.
- **Our D3DX stays in charge.** The game's imports still bind to the native D3DX of plans 4-7. Five entry points forward into the lifted DLL. HLSL effect text goes through the lifted effect compiler (`D3DXCreateEffectCompiler`, then `ID3DXEffectCompiler::CompileEffect`) to fx_2_0 bytes, and those take plan 5's existing path, so every `ID3DXEffect` the game holds is still ours. `D3DXCompileShader`, the fragment linker and the sphere hand the game the lifted DLL's own COM objects (buffers, constant tables, linker, mesh), which reach our device through its vtable like any guest code.
- **The lifted DLL is loaded lazily,** at the first call that needs it, from `d3dx9_25.dll` beside the engine binary (the build copies the rebased image to `out/d3dx9_25.dll`). It is mapped at its lifted base, registered under its own module name (`bw2-d3dx9_25-lifted.dll`, so the game's `GetModuleHandleA("d3dx9_25.dll")` never finds it), its imports are bound by name like the game's, and its entry runs as `DllMain`. Its msvcrt imports get new answers in `runtime/bw2/shims_crt.c`, its kernel32 ones in `runtime/bw2/shims_k32.c`, and its one data import (`_adjust_fdiv`) points at a guest dword; an import nobody answers stops loudly by name when called.
- **D3DX's run-time questions are answered on purpose:** its shader-validator lookup in `d3d9.dll` gets an accept-all validator (Ruling 12), its `DebugSetMute` lookup a no-op, and its CPU check a CPU consistent with our `cpuid` (Ruling 8).
- **Next layer:** with the effect compiled, the game draws its menus for some hundreds of frames (741 in the spike; the count depends on timing) and then calls `_BinkOpen@8`, plan 10's layer.

**Tech Stack:** C (clang, arm64, macOS 13+), the pcrecomp lifter and win32hle (vendored, MIT), Python 3.14 with pefile and capstone, `/usr/bin/tar` (bsdtar 3.5.3 / libarchive 3.7.4, part of macOS), pytest.

**Spec:** `docs/superpowers/specs/2026-11-10-bw2-macos-port-design.md` (sections 5.1, 5.2 D3DX, 6.4, 8, 9, 11). Facts: `docs/research/input.md` (where plan 6 stops), `shaders.md`, `d3dx-usage.md`, `build-pipeline.md`.

## Review Focus

- **A compile error.** A game effect that fails to compile must come back as the HRESULT and error buffer Microsoft's D3DX gives, never as a crash, a hang or a half-built effect; the game's own retry (2 calls, "Measured" item 3) then works as on Windows. (Task 5, check `hlsl_effect_error`: a deliberately broken effect gives a failing HRESULT, `*ppEffect` NULL, and an error buffer whose text names line 3.)
- **Lifted objects meeting ours.** A lifted `ID3DXConstantTable::SetFloat` or `ID3DXMesh::DrawSubset` calls our device through its vtable, and our effect framework reads the CTAB of a shader the lifted compiler made. The game must see one consistent device: shaders the lifted code creates are our `IDirect3DVertexShader9`/`IDirect3DPixelShader9`, and constants it sets land in our device's constant registers. (Task 4, check `hlsl_constant_table`; Task 5, check `hlsl_sphere_draw`.)
- **Two compiles at once.** The lifted DLL uses its own critical sections and a global allocator. Threads interleave in the middle of a compile whatever the shims do: `RECOMP_BACKEDGE` yields (`host_lite.c` `yield_hook` -> `hle_yield`) and `Sleep` hand the machine to other threads. Correctness therefore rests on D3DX's own critical sections and on win32hle's `EnterCriticalSection` blocking correctly, not on holding the machine lock. The failure modes to watch are `EnterCriticalSection`/`LeaveCriticalSection` and `InterlockedExchange` semantics under contention, and the per-thread FPU state (`g_st`, `g_fp_top`, `g_fpu_cw`) and SSE registers being saved and restored across yields. (Task 4, check `hlsl_two_threads`: two guest threads each compile 20 shaders, every result's bytes equal the single-threaded result.)
- **SSE and SSE2 in the lifted D3DX.** With Ruling 8 the DLL takes its SSE/SSE2 code paths, which the lifter must get right: a wrong `movaps` alignment rule, `shufps` immediate, `cvt*` rounding mode (from `MXCSR`, not the x87 control word) or packed compare mask corrupts vectors and matrices silently. (Task 4, check `d3dx_cpu` pins the selection value and `hlsl_constant_table` checks a matrix end to end; Task 4 Step 4 lists SSE traps by mnemonic.)
- **The shader validator.** An accept-all validator must keep the arity of each method D3DX calls exactly (stdcall: a wrong pop count corrupts the guest stack). (Task 4, check `d3dx_validator`.)
- **The FPU state.** The compiler folds constants with x87 code and `_CIpow`/`floor`/`atof` through msvcrt. A helper that pushes or pops the wrong number of `g_st` slots corrupts the caller's floats silently. (Task 3, `crt_x87`: the stack depth after each helper is as documented, and a value under the operands survives; Task 6 compares the effects' literal and preshader values against the shipped binaries; a `state_value_differs` finding is checked for an FPU cause before it is recorded as a compiler-version difference.)
- **The lifted DLL in a fresh support folder and a packaged app.** The engine must find `d3dx9_25.dll` beside its own binary wherever that is (the repo's `out/`, later the app bundle), not in the working directory, and a missing file must stop loudly at the first HLSL call, not at start-up (engine tests without game files never need it). (Task 4, check `d3dx_missing`; Task 2, `test_d3dx_beside_engine`.)

### Task 1: d3dx9_25.dll from disc 1, pinned and rebased

**Files:**
- Create: `bw2/d3dx.py`, `tests/test_d3dxdll.py`.
- Modify: `.gitignore` only if `gamefiles/d3dx/` is not already covered by `gamefiles/` (it is; check, do not add a line that is not needed).

**Interfaces:**
- Consumes: `bw2.disc.open_disc`, `list_files`, `find`, `extract`, `identify_discs`; `bw2.paths.GAMEFILES`; `tests/fixtures.py`'s `make_pe(sections, imports, data_dirs=...)`.
- Produces (`bw2/d3dx.py`):
  - Constants: `CAB_PATH = "DIRECTX9/APR200~2.CAB"`, `CAB_SIZE = 1079850`, `CAB_SHA256 = "1fc43223b767ec0121989e2c07b56b48ccdd2895c3f638068d24d7869049214d"`, `DLL_NAME = "d3dx9_25.dll"`, `DLL_SIZE = 2337488`, `DLL_SHA256 = "4c54df27ce84d21b2924e64ff79b13e7876ce85d8e0c9c1d0abd8da73888187a"`, `LIFT_BASE = 0x08000000`, `REBASED_SHA256` (measured in Step 4 and pinned).
  - `extract_dll(disc1: Path, dest: Path) -> Path`: extracts `CAB_PATH` from the disc image (a `.cue`, `.bin` or `.iso` that `open_disc` takes) into a temporary folder under `dest`, checks its size and SHA-256, runs `/usr/bin/tar -xf <cab> -C <tmp> d3dx9_25.dll` with `env={"PATH": "/usr/bin:/bin"}` and `check=True`, checks the DLL's size and SHA-256, moves it to `dest / DLL_NAME` and removes the temporary folder. A mismatch raises `ValueError` naming the file, the expected and the found value.
  - `rebase(src: Path, dst: Path, base: int = LIFT_BASE) -> Path`: reads the base relocation directory (data directory 5). Each entry of type 3 (`IMAGE_REL_BASED_HIGHLOW`) adds `base - old_base` (mod 2^32) to the dword at its RVA; type 0 (`ABSOLUTE`, padding) is skipped; any other type raises `ValueError("relocation type <t> at RVA 0x<rva>")`. ## Rulings (my calls; the spec leaves them to the builder)

1. **Scope and phasing:** plan 9 answers HLSL compilation (`D3DXCreateEffect` given text, `D3DXCompileShader`, `D3DXCompileShaderFromFileA`), the fragment linker and `D3DXCreateSphere`, which closes D3DX's import list (spec 5.2: all 60 implemented). "Closed" is checked against the game's real inputs: the runtime effect (Task 7), the 15 self-contained `.sdv` sources (Task 6) and the 7 `.fx.caesar3` `D3DXCompileShader` sources (Task 6). The boot compiles one effect and then reaches Bink, which is plan 10's (spec 5.2 Video).
2. **The HLSL compiler is Microsoft's own**, lifted from `d3dx9_25.dll` in disc 1's `DIRECTX9/APR200~2.CAB`: the exact DLL `white.exe` imports, so its output matches what the game got from `D3DXCreateEffect` and `D3DXCompileShader` on Windows byte for byte (the `.sdv` binaries were made by an older compiler, Ruling 9). It is user-supplied material like `white.exe`: extracted, rebased, lifted and compiled on the user's Mac, never committed or shipped; only its catalog of addresses is committed (spec 9). Rejected: vkd3d-shader 2.1 (licence fits as a separate LGPL library, but no Homebrew formula, a from-source autotools build on the user's Mac, and an fx_2_0 writer that cannot emit `sampler_state` initializers, which the first runtime effect needs); writing our own HLSL compiler and fx_2_0 writer (a large compiler with no Windows reference to check it against); capture-and-precompile (needs a Windows `fxc`).
3. **CAB extraction with `/usr/bin/tar`:** macOS's bsdtar (libarchive, BSD licence) reads Microsoft CAB files with their compression. It ships with macOS, so there is no new dependency, no Homebrew package, and no GPL tool (cabextract) in the Builder.
4. **Rebased to `0x08000000`:** the DLL's own base `0x400000` is `white.exe`'s. `0x08000000`-`0x08253000` lies between the end of `white.exe` (`0x2451210`) and win32hle's "anywhere" allocations (from `0x10000000`, where ScriptLibraryR also sits), and is held from start-up like ScriptLibraryR's range. The rebase applies only HIGHLOW relocations (all the DLL has) with our own code; any other type stops loudly.
5. **Effects stay ours.** HLSL text is compiled by the lifted effect compiler into fx_2_0 bytes, which take plan 5's path, so the game holds only our `ID3DXEffect`s and pools, with one implementation of states, pools and preshaders. `D3DXCompileShader`, the fragment linker and the sphere give the game the lifted DLL's own objects (buffers, constant tables, linker, mesh); those reach our device through its vtable like the game's own code.
6. **Lazy load beside the engine:** the lifted DLL is opened at the first call that needs it, from `d3dx9_25.dll` in the engine binary's own folder (`out/` here, the app bundle later). Engine tests without game files never touch it, and a missing file stops loudly at the first HLSL call.
7. **msvcrt answers live in BW2's runtime** (`runtime/bw2/shims_crt.c`), not in vendored win32hle, and cover what the lifted D3DX reaches; every other msvcrt import stays a loud stop by name. The x87 helpers work on the lifted FPU stack as pcrecomp's `x87crt.c` documents. `setlocale` answers only the "C" locale, which is all D3DX asks for. Its kernel32 and GDI32 needs go to `shims_k32.c` (Ruling 13).
8. **The lifted D3DX sees one consistent CPU and takes its SSE/SSE2 paths.** D3DX's CPU check (`0x443DA2`, result at `[0x61129C]`, "Measured" item 12) asks `IsProcessorFeaturePresent` for every feature but SSE2 and probes SSE2 itself with `cpuid`, which `cpu.c` answers with SSE and SSE2 present. Left as it was, win32hle's "0 for everything" would show D3DX SSE2 present and SSE absent, a CPU that does not exist. Forcing the x87 paths would need either a `cpuid` that lies to the game too or a write into D3DX's data, both worse. So `IsProcessorFeaturePresent` (BW2's `shims_k32.c`, overriding win32hle; neither `white.exe` nor `ScriptLibraryR.dll` imports it) answers from `cpu.c`'s own feature bits, and the lifted D3DX takes the SSE/SSE2 code paths, which the lifter implements (`lift32_sse.py`; SSE is 7.5% of `white.exe`'s instructions). SSE lifter gaps are expected and handled in Task 4 Step 4; check `d3dx_cpu` pins the selection value at `[0x0821129C]`, and `hlsl.md` records the path it picks. `cpuid` is unchanged for the game.
9. **The oracle:** every `.sdv` ships its source beside the binary Lionhead compiled from it, so the 15 self-contained sources check the lifted compiler against Microsoft's output on the same input. That output came from an older Microsoft compiler (CTAB stamps 5.04.00.3900, against 9.06.168.0000 for this DLL, "Measured" item 5), so the oracle checks structure, not bytes: techniques, passes, shader versions and the shared parameters must agree, shaders are compared with comment tokens stripped, and differences a compiler version explains are recorded findings with their offsets, not failures (Task 6 defines which is which). The test reads the files in memory and stores nothing.
10. **`BW2_HLSL_LOG`** prints numbers, HRESULTs and profile names only, never shader text, like the other log switches.
11. **No C++ exception crosses the lifted D3DX:** it imports no `_CxxThrowException`, and the game reaches it only through the engine's shims, so `__CxxFrameHandler` and `_except_handler3` stay unanswered (loud if ever called). `_setjmp3` and `longjmp` stay unanswered too: their only callers are not reached from the five entry points ("Measured" item 8).
12. **D3DX's `d3d9.dll` lookups are answered on purpose.** The compiler looks up `Direct3DShaderValidatorCreate9` in `d3d9.dll` before validating each shader (`0x080F42EB`, `0x08149AE2`, `0x08165B6E`, "Measured" item 8), and today it would find no `d3d9.dll` and skip validation with nobody having decided it. `d3d9` becomes a win32hle system module (as on Windows, where it is always present; a one-line `third_party/pcrecomp` patch), and `Direct3DShaderValidatorCreate9` gives an accept-all validator whose methods return `S_OK`. Chosen over a validator that returns NULL, because what D3DX does with a NULL validator is an untested path, while with a validator that passes it runs exactly the Windows path for valid shaders; Microsoft's compiler output for shaders the game shipped is valid, and our `sm_decode` still rejects anything it does not know, loudly. Chosen over a loud stop, because the game passes flags 0 and so every compile asks. `DebugSetMute` (`0x08029B6D`) is a no-op in `d3d9.dll` (retail `d3d9.dll` exports it), and `d3d9d.dll`, the debug runtime, stays absent as on a retail machine: its `LoadLibraryA` gives 0, the one `[module] ... not found` line from the lifted D3DX the tests allow.
13. **Where the lifted D3DX's answers live, and its module name.** msvcrt in `shims_crt.c`, kernel32 and GDI32 in `shims_k32.c` (BW2's tables come first, so no vendored patch is needed for a missing name), data imports in `dll.c`'s `bw2_bind_resolve` (an unknown data import stops the load by name; it is never bound to a stub address, which would fault on the first read with no name). The lifted image is registered as `bw2-d3dx9_25-lifted.dll`, so win32hle's first-match `find_by_name` never hands the game the lifted DLL in place of our native D3DX.
14. **Discovery seeds from code-section relocations.** This DLL keeps its read-only data (vtables, function tables) in `.text`, where `reloc_data_targets` does not look, so `discover` gets a `code_reloc_seeds` option for it: relocated dwords in `.text` that lie outside decoded instructions and jump tables and point at plausible function starts. Off for the other three modules, so their catalogs do not change. What it misses shows up as an unresolved indirect call into the D3DX range and goes to `EXTRA_SEEDS` with its calling address, batched to keep the number of 16-minute discovery runs down.
