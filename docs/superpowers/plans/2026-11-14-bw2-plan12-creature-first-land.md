# Plan 12: The creature choice and the first land Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Scripted headless runs pick a creature in the first land, take the land's first tutorial (moving and looking around), play the land on to its end and load the second land, and keep a land session running for 10 minutes, with no stop. That moves the boot frontier from the creature choice into the campaign (spec section 2, "Done means").

**The two-click choice is measured on the port, not verified on Windows.** Every single click on a creature failed to pick it in the spike behind this plan, but two separate clicks on the same creature, 15 s apart, pick it, on the New Game path and on a loaded save alike ("Measured" items 3 and 4). The click reaches the game's input and its action bindings in the read it arrives ("Measured" item 5). The Windows VM cannot run the game (plan 11: no 3D device), so this is consistent with a select-then-confirm design (the first click asks for beam and meteor art) and equally with a port fault that eats or delays the first acceptance (the frame order of the `0x0056D439` clear, read timing), which a two-click script would hide. Task 2's bring-up records which binding the second click's acceptance goes through and what the first click's handler starts; only that evidence may call the two clicks the game's design, in this plan, in `land1.md` and in the spec. Until then the plan scripts two clicks and calls it "measured on the port". Fixes come only where a run stops or that evidence shows a fault.

**Architecture:**
- **A file anchor for scripts.** Plan 11's anchors are movies and wall time. The land's steps show no movie, but the game asks for files at known moments: the load opens the save's files, the first click on a creature asks for four art files that no install holds, and the choice asks for the scroll models ("Measured" item 4). `BW2_INPUT_SCRIPT` gains `after file <name>`, fed from `runtime/bw2/guard.c`'s existing `CreateFileA` and `CreateFileW` wrappers (the ones the game's imports reach, "The engine today"), which record the name and forward the call untouched. An anchor on a game event replaces a guessed wait, and a test that waits for it fails by name if the step did not happen.
- **One save after the choice.** The land tests start from saves, as plan 11's load test does. A second module fixture, `chosen_game`, loads plan 11's `saved_game`, picks the lion, waits for the tutorial offer and saves from the pause bar. The tutorial, land-end and soak tests then load that save: about 1 minute each, not 3.
- **Subtitles as a measuring aid only.** The game shows its advisors' lines as text when the profile's subtitle setting is on ("Measured" item 6). Bring-up runs turn it on in a scratch copy of the profile and read the frames to learn each step. Tests never depend on it, and no line of the game's text is written down; steps are described in neutral words with their places.
- **Next layer:** the second land and the rest of the campaign (plan 13 on), Bink audio tracks when a scene opens one of the 22 movies that have one (Ruling 7), and the Builder app and packaging once the campaign plays through.

**Tech Stack:** C (clang, arm64, macOS 13+), pcrecomp win32hle (vendored, MIT), Python 3.14 and pytest, capstone (already in the venv) for reading the exe during bring-up.

**Spec:** `docs/superpowers/specs/2026-11-10-bw2-macos-port-design.md` (sections 2, 5.2 Input and Files and saves, 7.4, 9, 11). Facts: `docs/research/saves.md` ("For the next plan"), `campaign.md`, `input.md`.

5. **The click's path in the exe.** The land reads the mouse only through `IDirectInputDevice8A::GetDeviceData` from `sub_009AFD20` (a traced load run: no `GetDeviceState`, `GetAsyncKeyState`, `GetKeyState` or `GetCursorPos` in the land). It asks for up to 0x200 elements of 0x14 bytes and walks them until an element's time stamp is 0, adding axis deltas times the sensitivity scale (`[0x1779230]`) and passing button changes to `sub_009AF310`, which sets bits in the input object at `0x1D73318`: the button state byte at `+0x110` (`0x1D73428`) and the per-frame event byte at `+0x15C` (`0x1D73474`). A down within `[0x1D7A664]` ms (the double-click time, `GetDoubleClickTime` = 500) of the button's previous down also sets the double-click bit. The action bindings poll these bytes through `sub_0064B4C0` (held), `sub_0064B590` (pressed), `sub_0064B5F0` (double) and `sub_0064B640` (released); in the probed run the left down set event bit 1 at read 5,274 and `sub_0064B590` consumed it at `0x0064B5DA` in that read. `0x0056D439` clears the event byte once per frame, after `sub_009AFD20`.

## Review Focus

- **Two clicks read as one double click.** Two downs closer than 500 ms set the game's double-click bit ("Measured" item 5), and a double click did not pick ("Measured" item 3). A script that spaces its clicks by read counts could fall under 500 ms at a high frame rate. The choice clicks are spaced by wall time, and the choice test asserts that the first click alone asked for no scroll model in its window (Task 2).
- **A file anchor on a name the game asks for only once per run.** The game caches its models: a name asked for before the anchor's window opened never comes again, and the test only times out. The window opens at the anchor read of the block before it, not at the file block's own arming, so a lookup caused by the previous block's own events (a click's down, pushed before its up arms the next block) counts, and a lookup from before that block does not (Task 1, cases `file_stale`, `file_window`, `file_window_early`). Each test's anchor names are ones the bring-up saw asked for first at that step.
- **A wrapper that is never reached, or that changes an answer.** The recorder lives in guard.c's `k_CreateFileA` and `k_CreateFileW`, the shims the game's imports resolve to; `createfile_forward` calls through `hle_resolve`, the real import path, and asserts both that the call was recorded and that its answer is unchanged: the same handle kind, the same last error (2 for a missing file, 183 after `OPEN_ALWAYS` on an existing one, as plan 11 measured), the same overlay redirection. The tripwire's device-path check comes first and is unchanged, and `g_allowed` stays empty. (Task 1; the whole suite runs after it.)
- **Drags that depend on the frame rate.** The land is moved and turned by holding a button while moving the mouse; a drag pushed as moves at fixed read numbers lasts 12 ms at one rate and 100 ms at another. Drags are moves spread over wall time (Task 3's `drag_blocks`), and the tutorial test runs three times, once with the Mac loaded.
- **A long land session.** Players spend hours in a land; leaks in textures, buffers, effects or audio grow until the process dies. The soak test samples the engine's resident size and asserts a measured bound on its growth (Task 5). (Dropped 2026-11-14: the user tests long sessions; no soak is run by agents.)
- **A save taken mid-scene.** `chosen_game` saves while the advisors offer the scrolls. If the load returns to another state (the offer gone, or the choice undone), every later test starts wrong. Task 2's bring-up checks the loaded state from frames, and its test asserts the scroll lookups on load; if the offer is gone, the tests replay the choice instead (Ruling 4).
- **An Escape that skips the offer.** `chosen_game` opens the pause bar with a held Escape while the advisors talk, and plan 11's `SKIP_STEPS` uses Escape to skip the land's scenes: the Escape may skip or dismiss the offer instead of opening the pause bar, and the game may refuse a save during a scripted scene. Task 2 Step 3 checks from frames that the Escape opened the pause bar with the offer still up; if not, it waits until the advisors finish, or applies Ruling 4's replay fallback, and records which.
- **A slow suite.** The new land tests are long. The land-end and soak tests carry the `long` marker and run only with `BW2_LONG=1` (Ruling 10); the default suite's new cost is recorded there.

**Interfaces:**
- Consumes: plan 11's block rules (arming, firing, anchor read `A`), `bw2_dinput_reads()`, guard.c's `k_CreateFileA` and `k_CreateFileW` (the shims the game's imports resolve to, "The engine today").
- Produces:
  - `void bw2_script_file(const char *guest_path)` in `input.h`: takes the last path component (after the last `\` or `/`). It ignores `NULL` and an empty component, and it is safe before the script is loaded (before the first read): such a call is counted (below) but recorded as no event, since no anchor window is open yet. After the load it records an event (the component and the read counter's value) only when the component equals, ASCII case-insensitively, the name of a file block not yet fired. It prints nothing and pushes nothing.
  - `unsigned long long bw2_script_files_seen(char *last, size_t n)` in `input.h`: how many calls with a non-`NULL` argument `bw2_script_file` has had, and a copy of the last one's component (kept in a fixed 260-byte buffer); used by the selftest only.
  - The event log is bounded: it holds only events whose name matches an unfired file block, and when a block fires with anchor read `A`, events recorded at a read before `A` are dropped (no later window starts before `A`). A log that would pass 256 events stops the run loudly with the read number (`d3d_fail`); nothing is dropped silently.
  - Script syntax `after file <name>`: `<name>` is the anchor's second field, one token like every anchor value (game file names have no spaces; `after file a b` is a bad line, "takes 2 fields"), 1 to 259 characters, with no `\` or `/`. `struct block`'s `words` grows from 64 to 272 bytes so the printed words hold `after file ` and 259 characters. **Window:** events recorded at or after the anchor read `A` of the block before it (for the first block after the absolute lines: from the first read). It is not the file block's own arming read, so a lookup the previous block's own events cause (a click's down, pushed in the same read as the previous anchor, before the up that lets this block arm) counts, and a lookup from before the previous block fired does not. The block fires at the first read, once armed, at which the log holds an event in its window whose name equals `<name>`; `A` is that first event's read value. It prints `[bw2] script: after file <name> at read <A>`, with `<name>` as written.
  - guard.c: `k_CreateFileA` calls `bw2_script_file(p)` after `device_path(p)`'s check and before `bw2_hle_shim("CreateFileA")()`; `k_CreateFileW` calls it with the narrowed name at the same place (an empty name for a `NULL` pointer, which it ignores). No new table entry anywhere, no change to `mount.c`; the device-path check and the empty `g_allowed` are unchanged.
  - `FRONT_FILE` in `tests/test_boot.py`: a file the front end asks for after its first read (Step 4 picks it from an `HLE_FILETRACE=1` boot).
