# Plan 9: HLSL from the disc's own D3DX, and the boot to Bink Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The game compiles its HLSL. `D3DXCreateEffect` given HLSL text, `D3DXCompileShader`, `D3DXCompileShaderFromFileA`, `D3DXCreateFragmentLinker` and `D3DXCreateSphere` are answered by Microsoft's own `d3dx9_25.dll` (the April 2005 DirectX redistributable on the user's disc 1), lifted to C like the game. The boot then gets past the profile dialog's tone-mapping effect and runs on to its first Bink call (exit 4, plan 10's layer).

**Architecture:**
- **The compiler is the one the game shipped with.** Disc 1 carries `DIRECTX9/APR200~2.CAB`, which holds the x86 `d3dx9_25.dll` that `white.exe` imports. The pipeline extracts it with macOS's own `/usr/bin/tar` (libarchive), checks its SHA-256, rebases it from `0x400000` (where `white.exe` sits) to `0x08000000` with its relocation table, discovers its functions and lifts it as a fourth module, `d3dx`. Only the catalog (addresses) is committed; the DLL, like `white.exe`, comes from the user's disc.
- **Our D3DX stays in charge.** The game's imports still bind to the native D3DX of plans 4-7. Five entry points forward into the lifted DLL. HLSL effect text goes through the lifted effect compiler (`D3DXCreateEffectCompiler`, then `ID3DXEffectCompiler::CompileEffect`) to fx_2_0 bytes, and those take plan 5's existing path, so every `ID3DXEffect` the game holds is still ours. `D3DXCompileShader`, the fragment linker and the sphere hand the game the lifted DLL's own COM objects (buffers, constant tables, linker, mesh), which reach our device through its vtable like any guest code.
- **The lifted DLL is loaded lazily,** at the first call that needs it, from `d3dx9_25.dll` beside the engine binary (the build copies the rebased image to `out/d3dx9_25.dll`). It is mapped at its lifted base, its imports are bound by name like the game's, and its entry runs as `DllMain`. Its msvcrt imports get new answers in `runtime/bw2/shims_crt.c`; an import nobody answers stops loudly by name when called.
- **Next layer:** with the effect compiled, the game draws its menus for about 740 more frames and then calls `_BinkOpen@8`, plan 10's layer.

**Tech Stack:** C (clang, arm64, macOS 13+), the pcrecomp lifter and win32hle (vendored, MIT), Python 3.14 with pefile and capstone, `/usr/bin/tar` (bsdtar 3.5.3 / libarchive 3.7.4, part of macOS), pytest.

**Spec:** `docs/superpowers/specs/2026-11-10-bw2-macos-port-design.md` (sections 5.1, 5.2 D3DX, 6.4, 8, 9, 11). Facts: `docs/research/input.md` (where plan 6 stops), `shaders.md`, `d3dx-usage.md`, `build-pipeline.md`.

6. **The disc's D3DX.** Disc 1's `DIRECTX9/` holds the April 2005 redistributable: `APR200~1.CAB` (the x64 DLL, 3,823,312 bytes), `APR200~2.CAB` (1,079,850 bytes, SHA-256 `1fc43223b767ec0121989e2c07b56b48ccdd2895c3f638068d24d7869049214d`) and `APR200~3.CAB` (managed DirectX). `/usr/bin/tar -tvf` lists `APR200~2.CAB`'s `d3dx9_25.dll` as 2,337,488 bytes, dated Mar 18 2005, and extracts it with SHA-256 `4c54df27ce84d21b2924e64ff79b13e7876ce85d8e0c9c1d0abd8da73888187a`.
7. **The DLL.** PE32, ImageBase `0x400000` (the same as `white.exe`, which spans `0x400000`-`0x2451210`), SizeOfImage `0x253000`. Sections `.text` (RVA `0x1000`, virtual size `0x20FEC3`; read-only data is merged into it), `.data` (`0x211000`, `0x304AC`), `.rsrc` (`0x388`), `.reloc` (directory `0x243000`, `0xF070` bytes). No TLS, no delay imports, no RTTI. Imports: KERNEL32 71, msvcrt 68, GDI32 26, ADVAPI32 3; 164 of the 168 are called from code (unreferenced: `InterlockedCompareExchange`, `IsBadReadPtr`, `FindResourceW`, and `_adjust_fdiv`, a data import). No `d3d9.dll` import. 323 exports; at the original base: `D3DXCompileShader` `0x4EB93A`, `D3DXCompileShaderFromFileA` `0x4EB45C`, `D3DXCreateEffectCompiler` `0x4F910A`, `D3DXCreateEffect` `0x4F9E22`, `D3DXCreateFragmentLinker` `0x56909B`, `D3DXCreateSphere` `0x4CC4B8`, `D3DXAssembleShader` `0x4EB374`.
8. **What the compiler calls.** Following direct calls only (virtual calls are not followed, so this is a lower bound), `D3DXCompileShader` reaches 187 functions and 36 imports: `??2@YAPAXI@Z`, `??3@YAXPAX@Z`, `free`, `_strdup`, `_stricmp`, `_vsnprintf`, `strchr`, `tolower`, `isalnum`, `isalpha`, `isdigit`, `isxdigit`, `atof`, `floor`, `_finite`, `_isnan`, `_controlfp`, `setlocale`, `_CIacos`, `_CIasin`, `_CIpow`, and kernel32's critical sections, `InterlockedExchange`, `Sleep`, `GetSystemInfo`, `VirtualAlloc`, `VirtualFree`, `UnmapViewOfFile`, `DeleteObject`, `GetCurrentProcess`, `SetUnhandledExceptionFilter`, `UnhandledExceptionFilter`, `TerminateProcess` (the last four are the CRT's security-cookie failure path). `D3DXCreateEffectCompiler` reaches a subset. `D3DXCreateSphere` adds `GetModuleHandleA` and `RegOpenKeyA`/`RegQueryValueExA`/`RegCloseKey`. `_setjmp3` (6 callers, `0x4E09D1`-`0x5D9009`), `longjmp`, the file functions (`fopen`, `_wfopen`, `_tempnam`) and `LoadLibraryA` are not reached by direct calls from any of the five entry points.
9. **The alternatives.** vkd3d-shader 2.1 (2026-08, LGPL-2.1+) has no Homebrew formula, so the Builder would have to build it from source with autotools on the user's Mac. Its fx_2_0 writer (`libs/vkd3d-shader/fx.c`, `write_fx_2_object_initializer`) stops with "Writing fx_2_0 sampler objects initializers is not implemented" on every `sampler_state` initializer, which the first runtime effect and 25 of the 59 sources use. The spec's capture-and-precompile fallback needs a Windows `fxc`, and there is no Windows reference (spec 11).
10. **Discovery on the rebased image** (pcrecomp's `rtti.py`, `vtable_scan.py`, `disasm32.py` through `bw2.discover.discover`, on a copy rebased to `0x08000000` in a scratch folder): 0 RTTI seeds, an 18 KB vtable seed list, a 2.8 KB merged seed list. The first `disasm32` round was still running after 16 minutes (single-threaded; white.exe's whole discovery took 455 s on 8 MB of `.text`). Task 2 records the final numbers.
11. **Absent** in every spike run: any disc, volume or driver question, any tripwire, anything from the protection VM.

**The engine today:** `runtime/bw2/d3dx/fx_effect.c` stops with `d3d_later("D3DXCreateEffect (HLSL source)")` when the data does not start with the fx_2_0 magic. `runtime/bw2/later.c`'s `g_later_names` lists `D3DXCompileShader`, `D3DXCompileShaderFromFileA`, `D3DXCreateFragmentLinker` and `D3DXCreateSphere`. `runtime/bw2/dll.c` maps a lifted DLL at its base without relocating it, binds its imports with `recomp_pe_bind(&img, hle_resolve_or_stub)` (an unanswered import becomes a stub that stops loudly when called), registers it with `hle_module_add`, `bw2_tls_add_module` and `bw2_eh_add_image`, and runs its entry as `DllMain`; today only for the game's own `LoadLibraryA`. `hle_call_guest(va, nargs, args)` calls guest code from a shim. win32hle has no msvcrt answers; pcrecomp's `runtime/native32/x87crt.c` (MIT) documents how msvcrt's x87 helpers work on the lifted FPU stack (`g_st`, `g_fp_top`, `fp_push_impl`/`fp_pop_impl` in `recomp_types.h`). `hle_guest_format(out, n, fmt, args)` formats a guest printf call. win32hle's `IsProcessorFeaturePresent` answers 0 for every feature.

## Global Constraints

- Never commit game material: exes, DLLs (`d3dx9_25.dll` included, original or rebased), CAB files, extracted files, strings, bytes, shaders, effects, assembly or HLSL text from the game, frames, or generated C. Facts only (addresses, sizes, counts, hashes). The committed catalog `bw2/catalog/d3dx9_25-apr2005.functions.json` holds addresses and flags only, like the others. No test or switch writes the game's shader text, compiled shaders or effects to disk; tests that read the `.sdv` files read them in memory from the game tree. Run `.venv/bin/python third_party/pcrecomp/tools/audit_repo.py .`, which must report CLEAN, before any commit that adds data.
- Docs (this plan, `hlsl.md`, the spec) never quote the game's shader text or its own output. They describe a source or a line in neutral words (counts, profiles, feature names) with the address or file that makes it. Test sources never contain the game's strings or shader text; every HLSL and assembly text in a test is written for the test.
- **Standing rule (user):** if the VM or the code it runs asks for a disc or driver check, stop and ask the user. The tripwire stays on, and its allow list (`runtime/bw2/guard.c` `g_allowed`) stays empty. Winsock keeps answering "no network". The lifted D3DX is not the protection VM; a disc, volume or driver question from it stops the run all the same and goes to the user.
- Fail loudly, never return 0 silently:
  - A lifted D3DX import that no table answers stops when called (`recomp_pe_bind` with `hle_resolve_or_stub`), naming the import. No msvcrt function is answered with a silent 0.
  - `_purecall` and `?terminate@@YAXXZ` stop with `[bw2] FATAL: msvcrt: <name>` and the guest address.
  - A missing or mismatched `d3dx9_25.dll` beside the engine stops with `[bw2] FATAL: d3dx9_25.dll (lifted): <reason>` at the first call that needs it, naming the path.
  - The rebaser and the extractor raise `ValueError` naming what did not match (hash, size, relocation type and RVA).
- **Later plans' layers** each exit 4 with `[bw2] reached <name>: owned by a later plan`. Bink (`binkw32.dll`, `_BinkOpen@8` and the rest), `dinput.dll`, `openal32.dll` and `wrap_oal.dll` stay as they are. `D3DXCompileShader`, `D3DXCompileShaderFromFileA`, `D3DXCreateFragmentLinker` and `D3DXCreateSphere` leave `g_later_names`, and the `D3DXCreateEffect (HLSL source)` stop goes. This plan's boot ends at `_BinkOpen@8`.
- **`bw2.h` does not change** (every lifted shard includes it). New cross-file functions are declared `extern` where used, as `register.c` does, or in `runtime/bw2/d3dx/d3dx.h` (a 2-minute relink).
- Exit codes are unchanged: 0 normal (including `BW2_QUIT_AFTER_READS`), 2 boot failure, 3 tripwire, 4 later plan's layer, `abort()` otherwise.
- Headless (`BW2_HEADLESS=1`) for every test. Tests that need the lifted DLL need the disc and carry `@pytest.mark.gamefiles` (`BW2_GAMEFILES=1`).
- Changes inside `third_party/pcrecomp/` are small, separate commits, each with one line in `third_party/pcrecomp.PATCHES` (path relative to `third_party/pcrecomp`, what changed and why). No NFSU2Recomp code; no Wine, ReactOS or vkd3d code is read into this repo. msvcrt answers follow the C and msvcrt documentation; the x87 helpers follow pcrecomp's `x87crt.c` description.
- External tools are called by absolute path with a fixed `PATH=/usr/bin:/bin`: `/usr/bin/tar` only. No new Homebrew package and no new Python package.
- Generated documents use only the ASCII hyphen-minus. Commit subjects are short and imperative, with no body or trailers. Never push, never add a remote, never change git config, and never write the user's real name or email anywhere. Work on branch `plan9`.

## Review Focus

- **A compile error.** A game effect that fails to compile must come back as the HRESULT and error buffer Microsoft's D3DX gives, never as a crash, a hang or a half-built effect; the game's own retry (2 calls, "Measured" item 3) then works as on Windows. (Task 5, check `hlsl_effect_error`: a deliberately broken effect gives a failing HRESULT, `*ppEffect` NULL, and an error buffer whose text names line 3.)
- **Lifted objects meeting ours.** A lifted `ID3DXConstantTable::SetFloat` or `ID3DXMesh::DrawSubset` calls our device through its vtable, and our effect framework reads the CTAB of a shader the lifted compiler made. The game must see one consistent device: shaders the lifted code creates are our `IDirect3DVertexShader9`/`IDirect3DPixelShader9`, and constants it sets land in our device's constant registers. (Task 4, check `hlsl_constant_table`; Task 5, check `hlsl_sphere_draw`.)
- **Two compiles at once.** The lifted DLL uses its own critical sections and a global allocator. Two guest threads compiling at the same time must neither deadlock nor corrupt each other, which holds only while every lifted D3DX call runs under the machine lock like other guest code and nothing in this plan's shims drops it (`hle_block_begin`) in the middle of a compile. (Task 4, check `hlsl_two_threads`: two guest threads each compile 20 shaders, every result's bytes equal the single-threaded result.)
- **The FPU state.** The compiler folds constants with x87 code and `_CIpow`/`floor`/`atof` through msvcrt. A helper that pushes or pops the wrong number of `g_st` slots corrupts the caller's floats silently. (Task 3, `crt_x87`: the stack depth after each helper is as documented, and a value under the operands survives; Task 6 compares constants in compiled shaders against the game's precompiled ones.)
- **The lifted DLL in a fresh support folder and a packaged app.** The engine must find `d3dx9_25.dll` beside its own binary wherever that is (the repo's `out/`, later the app bundle), not in the working directory, and a missing file must stop loudly at the first HLSL call, not at start-up (engine tests without game files never need it). (Task 4, check `d3dx_missing`; Task 2, `test_d3dx_beside_engine`.)

- Produces (`bw2/d3dx.py`):
  - Constants: `CAB_PATH = "DIRECTX9/APR200~2.CAB"`, `CAB_SIZE = 1079850`, `CAB_SHA256 = "1fc43223b767ec0121989e2c07b56b48ccdd2895c3f638068d24d7869049214d"`, `DLL_NAME = "d3dx9_25.dll"`, `DLL_SIZE = 2337488`, `DLL_SHA256 = "4c54df27ce84d21b2924e64ff79b13e7876ce85d8e0c9c1d0abd8da73888187a"`, `LIFT_BASE = 0x08000000`, `REBASED_SHA256` (measured in Step 4 and pinned).
  - `extract_dll(disc1: Path, dest: Path) -> Path`: extracts `CAB_PATH` from the disc image (a `.cue`, `.bin` or `.iso` that `open_disc` takes) into a temporary folder under `dest`, checks its size and SHA-256, runs `/usr/bin/tar -xf <cab> -C <tmp> d3dx9_25.dll` with `env={"PATH": "/usr/bin:/bin"}` and `check=True`, checks the DLL's size and SHA-256, moves it to `dest / DLL_NAME` and removes the temporary folder. A mismatch raises `ValueError` naming the file, the expected and the found value.
  - `rebase(src: Path, dst: Path, base: int = LIFT_BASE) -> Path`: reads the base relocation directory (data directory 5). Each entry of type 3 (`IMAGE_REL_BASED_HIGHLOW`) adds `base - old_base` (mod 2^32) to the dword at its RVA; type 0 (`ABSOLUTE`, padding) is skipped; any other type raises `ValueError("relocation type <t> at RVA 0x<rva>")`. It then writes `base` into OptionalHeader.ImageBase and nothing else: the checksum, the relocation directory and every other byte stay. It is pure Python on the file bytes (`struct`; `pefile` only to map RVAs to file offsets), and the same input gives the same output.
  - `d3dx_dll(gamefiles: Path = GAMEFILES) -> Path`: the rebased image `gamefiles/d3dx/d3dx9_25.0x08000000.dll`. When it is missing, it finds disc 1 under `gamefiles/discs` with `identify_discs`, calls `extract_dll` into `gamefiles/d3dx/` and `rebase`. When it exists and its SHA-256 is `REBASED_SHA256`, it returns it without writing anything. A rebased file with another hash raises `ValueError`.
  - `main(argv=None) -> int` (`python -m bw2.d3dx`): makes the rebased image and prints its path and hash. Task 2 adds `--catalog`.

## Rulings (my calls; the spec leaves them to the builder)

1. **Scope and phasing:** plan 9 answers HLSL compilation (`D3DXCreateEffect` given text, `D3DXCompileShader`, `D3DXCompileShaderFromFileA`), the fragment linker and `D3DXCreateSphere`, which closes D3DX's import list (spec 5.2: all 60 implemented). The boot compiles one effect and then reaches Bink, which is plan 10's (spec 5.2 Video).
2. **The HLSL compiler is Microsoft's own**, lifted from `d3dx9_25.dll` in disc 1's `DIRECTX9/APR200~2.CAB`: the exact DLL `white.exe` imports, so its output matches what the game got on Windows byte for byte. It is user-supplied material like `white.exe`: extracted, rebased, lifted and compiled on the user's Mac, never committed or shipped; only its catalog of addresses is committed (spec 9). Rejected: vkd3d-shader 2.1 (licence fits as a separate LGPL library, but no Homebrew formula, a from-source autotools build on the user's Mac, and an fx_2_0 writer that cannot emit `sampler_state` initializers, which the first runtime effect needs); writing our own HLSL compiler and fx_2_0 writer (a large compiler with no Windows reference to check it against); capture-and-precompile (needs a Windows `fxc`).
3. **CAB extraction with `/usr/bin/tar`:** macOS's bsdtar (libarchive, BSD licence) reads Microsoft CAB files with their compression. It ships with macOS, so there is no new dependency, no Homebrew package, and no GPL tool (cabextract) in the Builder.
4. **Rebased to `0x08000000`:** the DLL's own base `0x400000` is `white.exe`'s. `0x08000000`-`0x08253000` lies between the end of `white.exe` (`0x2451210`) and win32hle's "anywhere" allocations (from `0x10000000`, where ScriptLibraryR also sits), and is held from start-up like ScriptLibraryR's range. The rebase applies only HIGHLOW relocations (all the DLL has) with our own code; any other type stops loudly.
5. **Effects stay ours.** HLSL text is compiled by the lifted effect compiler into fx_2_0 bytes, which take plan 5's path, so the game holds only our `ID3DXEffect`s and pools, with one implementation of states, pools and preshaders. `D3DXCompileShader`, the fragment linker and the sphere give the game the lifted DLL's own objects (buffers, constant tables, linker, mesh); those reach our device through its vtable like the game's own code.
6. **Lazy load beside the engine:** the lifted DLL is opened at the first call that needs it, from `d3dx9_25.dll` in the engine binary's own folder (`out/` here, the app bundle later). Engine tests without game files never touch it, and a missing file stops loudly at the first HLSL call.
7. **msvcrt answers live in BW2's runtime** (`runtime/bw2/shims_crt.c`), not in vendored win32hle, and cover what the lifted D3DX reaches; every other msvcrt import stays a loud stop by name. The x87 helpers work on the lifted FPU stack as pcrecomp's `x87crt.c` documents. `setlocale` answers only the "C" locale, which is all D3DX asks for.
8. **The lifted D3DX sees no SSE or 3DNow!** (`IsProcessorFeaturePresent` answers 0, as win32hle does today), so it takes its plain x87 code paths. `cpuid` is unchanged for the game.
9. **The oracle:** every `.sdv` ships its source beside the binary Lionhead compiled from it, so the 15 self-contained sources check the lifted compiler against Microsoft's output on the same input. The test reads them in memory and stores nothing.
10. **`BW2_HLSL_LOG`** prints numbers, HRESULTs and profile names only, never shader text, like the other log switches.
11. **No C++ exception crosses the lifted D3DX:** it imports no `_CxxThrowException`, and the game reaches it only through the engine's shims, so `__CxxFrameHandler` and `_except_handler3` stay unanswered (loud if ever called). `_setjmp3` and `longjmp` stay unanswered too: their only callers are not reached from the five entry points ("Measured" item 8).
