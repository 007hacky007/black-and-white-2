# Plan 14: Performance, the frame's waits Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The game spends less of each frame waiting: on the GPU it has not yet been given work, on guest threads that poll for events, and on guest memory accesses the compiler may not optimise. A meter and a quiet-Mac bench show where a frame's time goes, before and after each change (spec 11: "Performance target: smooth at native resolution on an M1-class Mac").

**Architecture:**
- **Measure first, with the user's rule built in.** `BW2_PERF=1` makes the engine print one line a second (presents, GPU time, time the game waits for its GPU query, draws, passes, command buffers, machine hand-overs and wait polls) and a total at exit. `tools/perf_bench.py` boots to the creature choice headless, reads those lines over a fixed window and prints a summary, but only on a quiet Mac; otherwise it prints `not measured: Mac under load (load X)` and starts nothing (Task 1).
- **Three costs measured in the land** ("Measured" items 3 to 6), one task each: guest threads parked in `INFINITE` waits poll every 200 us and make the game's thread hand the machine over thousands of times a second (Task 2, win32hle waits on a condition variable); the frame's whole command buffer is sent to the GPU only at `Present`, so the game's per-frame event query waits for all of the GPU's work after the CPU is done (Task 3, commit at pass boundaries); pcrecomp's `MEM*` macros are `volatile`, so clang keeps every guest load and store (Task 4, spec 7.1 and `build-pipeline.md` "Known items").
- **The record** (Task 5): `docs/research/performance.md` with every number and the load it was taken at, the spec's notes, and what comes next.
- **Next layer:** after this plan, gameplay faults from the user's own reports; further performance work only where the meter shows a cost (native resolution in a window is the user's to try, see Ruling 6).

**Tech Stack:** C and Objective-C (clang, arm64, macOS 13+, Metal), pthreads (`pthread_cond_timedwait`), Python 3.14 (pytest), `/usr/bin/sample` for profiles.

**Spec:** `docs/superpowers/specs/2026-11-10-bw2-macos-port-design.md` (sections 2, 5, 7.1, 7.2, 7.3, 11). Facts: `docs/research/build-pipeline.md` ("Known items for later plans"), `campaign.md` ("Frame rates (headless)"), `land1.md`, `saves.md`, `builder.md` ("For the next plan").

## Measured before writing (2026-11-15)

Main at `a59a168`, `out/bw2` relinked (143,626,216 bytes), an Apple Silicon Mac with 10 cores. The spikes ran on a throwaway branch `spike-perf` (deleted; `out/bw2` rebuilt from main afterwards) with timers printed once a second; nothing taken from the game was kept.

1. **The boot today.** `BW2_HEADLESS=1 BW2_QUIT_AFTER_READS=300 out/bw2 --game gamefiles/game` ends `[bw2] quit after 300 input reads (BW2_QUIT_AFTER_READS)` (the run's own limit, not an unanswered layer), exit 0, 78 lines, no loud line. No layer is unanswered; scripted runs reach the first land (plan 12) and the app is built by the Builder (plan 13). The user's order now is performance.
2. **The scene measured.** `NEW_GAME_SCRIPT + SKIP_TO_CHOICE` from `tests/test_boot.py` (41 script anchors, the last about 64 s after start) leaves the game at the creature choice in the first land, drawn in 3D at 1024x768 (the game's default; the headless desktop is 1920x1080, `d3d9_adapter.c:18`). Per frame there: 339 draws, 22 render passes, 1 blit encoder and 1 command buffer (the same in every second counted). The front end, for comparison, runs at 40 Presents a second paced by the game's own `Sleep(n >= 3)` (40 a second), 22 draws a frame.
3. **The game waits for its GPU each frame.** At `0x00935AB0` (inside the lifted `sub_009F3B40`) the game loops `while (q->GetData(NULL, 0, D3DGETDATA_FLUSH) == S_FALSE) { [esi+0xB0]++; if (!byte [0x1D6D870]) Sleep(0); }` on an `IDirect3DQuery9` at `[esi+0xA8]` (vtable `+0x1C`; `Sleep` through IAT `0xC12180`). In the land that loop made 1.4 to 1.9 million `Sleep(0)` calls a second (a rate taken under load, so only its size matters: the game's thread spins there every frame). Our command buffer is committed only at `Present` (`mtl_present`) or at `GetData(FLUSH)` (`d3d9_query.m:80`), so the GPU starts the frame's 22 passes only after the CPU has recorded all of them, and the CPU then waits for all of them.
4. **Four guest threads poll.** Four guest threads sit in `WaitForSingleObjectEx(h, INFINITE)` (through `sub_00880990`; host stacks `hle_wait+608` in `usleep` and `+612` in `hle_block_end`). `hle_wait` (`kernel32.c:448`) checks, gives the machine up, sleeps 200 us and takes it back, so the four made about 12,000 polls a second (under load, as are the rates below), all of `INFINITE` waits (no finite or zero-timeout wait started in the land; contended critical sections about 0 a second). Each poll that finds the machine taken makes `g_waiters` non-zero, and the game's thread then hands the machine over at its next import (`shim_entry` calls `hle_yield`): about 4,100 to 5,300 hand-overs a second.
5. **Guest memory is volatile.** `third_party/pcrecomp/runtime/recomp32/recomp_types.h:227-232` cast every `MEM8`..`MEMD` through `volatile`. A build without it (all 208 objects, 177 s at load 33 to 89) is 141,430,760 bytes (2.2 MB smaller) and boots to the same quit line, exit 0. The hottest guest functions in the land are SSE math (`sub_00AAF420`: 57 `movss`, 54 `movaps`, 19 `subss`, 18 `mulss` in 740 lines), where every operand is a guest load.
6. **Where the game's thread spends its time (indicative only, taken under load).** A 10 s `/usr/bin/sample` of the engine at the choice, on a busy Mac (load about 5 on 10 cores), self time on the game's thread: lifted guest code 42%, `sched_yield`, mutex waits and hand-overs 28.5% (the GPU-query spin's `Sleep(0)` and `hle_yield` at imports), other host code 17%, Objective-C and Metal 9.4%, our D3D9 layer's own functions 3%; `recomp_lookup` 2%, `NSData` keys of the pipeline caches about 1%. The four other guest threads spent about 80% asleep in `hle_wait`'s `usleep` and about 19% waiting for the machine's mutex. Not a measurement: no number here sets a bound or a choice beyond which costs to look at.
7. **Frame rates: not measured: Mac under load** (seven checks ten minutes apart over an hour, about 04:15 to 05:15: 1-minute load 2.9 to 83.6 on 10 cores, and a process above 50% CPU at five of the seven: dotnet at 99%, a browser at 57 to 72%). The spike's per-second counts above are counts, not times; its times were all taken under that load and are not recorded.
8. **What is safe to change.** No host thread writes guest memory outside the machine lock: the audio sink (`ds_out.m` `sink_main`) only reads guest buffers under the mixer's own mutex, winmm's timer threads take the machine (`mach_enter`) before `hle_set_event` or a callback, and Metal's completion handlers touch only host fields (`completed`, the in-flight semaphore). Every render pass begins with `MTLLoadActionLoad` and ends with `MTLStoreActionStore` (`mtl_device.m:440-452`; `mtl_begin_pass_if_needed` starts at 428 and makes the render encoder at 463) and nothing uses multisampling, so a command buffer can end at any pass boundary without losing a target's contents. Occlusion counts live in per-query slots of one shared buffer and are read only after the query's serial completes (`mtl_device.m:389-421`; `mtl_occlusion_end` takes the open buffer's serial), so they survive a commit between `Begin` and `End`. Signals that change what `try_take` answers: `SetEvent`, `hle_set_event` (winmm's event timers), `ReleaseMutex`, `ReleaseSemaphore`, a thread's end (`hle_thread_done`), `LeaveCriticalSection` for `hle_enter_cs`; `ResetEvent` and `PulseEvent` only clear. All of them run under the machine except one: `thread_trampoline` sets `a->done = 1` after `hle_call_guest` has already called `mach_leave` (`kernel32_crt.c:43-44`, `host_lite.c:316`; `ExitThread` sets it under the machine, `kernel32_crt.c:77`). Draw-time serials: a draw marks its vertex and index buffers used at `mtl_serial()` (`d3d_buffer_for_draw`, `d3d9_buffer.c:119`) and frees its UP, fan and realigned index copies after `mtl_serial()` (`d3d9_draw.c:168/240/272`); `draw_up` makes its UP copies before `draw()` runs. `hle_wait`'s `all` branch takes each object as it checks it and does not undo a partial take (`kernel32.c:452-454`), so an `all` wait on an auto-reset event and a semaphore set at different times never returns today.

## Review Focus

- **A wake that never comes.** With polling gone, a state change that forgets to wake the waiters leaves a guest thread asleep until the backstop, a silent stall. Every place that can make `try_take` answer 1 must call `hle_wake`, and the backstop must catch and name any it missed. Task 2's tests cover each signal (event, timer event, semaphore, mutex, thread end, critical section), and the boot tests' `LOUD` list gains `missed wake`, so a missed one fails every boot test.
- **A lost wake from a signal raised outside the machine.** The sleeping wait is race-free only because the waiter registers as a sleeper and reads the wake generation while it still holds the machine, and every signaller calls `hle_wake` while holding it. A signal raised outside the machine (a thread's end in `thread_trampoline` today, any host-side signaller later) can fall between the waiter's last check and its sleep, and the waiter then sleeps until the backstop (`missed wake`). Task 2 moves the thread end under the machine; `test_wait_thread_end_race` (50 workers that end with no `Sleep`, each raced by the main thread's wait) pins it with `missed wakes == 0`.
- **A wait that must still time out, and `WaitForMultipleObjects` with `all`.** A finite timeout must end at its time even with no signal, a zero timeout must not sleep at all, and an `all` wait takes its objects only when every one is ready (Windows semantics; today's take-as-it-checks loses an auto-reset event's signal and hangs). Task 2's `test_wait_timeout_still_times_out`, `test_wait_zero_does_not_sleep` and `test_wait_all_two_objects` (an auto-reset event and a semaphore set 200 ms apart).
- **Per-draw resources tracked to the wrong command buffer.** After an early commit, the draw that opens the new pass is recorded into buffer S+1; its vertex and index buffers' in-use serial and the heap's free-after serial of its UP, fan and realigned index copies must be S+1 too. If the commit came after any of them read `mtl_serial()` (for example inside `mtl_draw`, or after `draw_up`'s copies), a `Lock(0)` on that buffer or a reused heap block would overwrite data the GPU has not read yet: silently wrong rendering (a spec 2 anti-goal). Task 3 commits only at a chunk point that runs before anything reads a serial for the command, and the `chunks` case `serials_follow_commit` checks the serials and the rendered colour end to end.
- **Handles across the commit.** `mtl_commit` drains the autorelease pool (`drain_pool`). The chunk point runs before `ff_build`, so no `struct ff_draw` exists when it commits; the handles an `ff_draw` later carries (heap buffers, texture views, pipeline libraries) are `__bridge_retained` in any case, and a mid-frame drain already happens today at the 64 MB staging bound (`staged`, `mtl_device.m:179-182`).
- **The game's own spin-waits on memory.** Without `volatile`, clang may keep a guest value in a register across a loop. A loop that waits for another guest thread's store must still see it, through the back-edge hand-over or an import in the loop. Task 4 keeps `test_spin_wait_hands_over` and adds `test_spin_wait_across_import`.
- **Render targets and queries across an early commit.** A target drawn in one command buffer and read (sampled, stretched, read back, presented) in the next must hold what was drawn; an event query must be done only when the work before its `Issue(END)` is; an occlusion query spanning a commit must count both parts. Task 3's `chunks` selftest group.
- **A meter that changes what it measures, or leaks into the user's log.** `BW2_PERF` unset must print nothing and cost only a branch per counter; set, it must not read back frames (the frame log does) or allocate per frame. Task 1's `test_perf_off_prints_nothing` and the bench's comparison of a run with and without the meter (recorded, not asserted). Its total line comes after the run's end line, so the app's watcher must not take it as the decisive line (Task 1's watcher cases in `tests/test_app_engine.py`).

### Task 2: Waits that sleep until something is signalled

**Files:**
- Modify: `third_party/pcrecomp/runtime/win32hle/kernel32.c` (`try_take` gains a peek mode, `hle_wait`, `hle_enter_cs`, `hle_leave_cs`, `k_SetEvent`, `hle_set_event`, `k_ReleaseMutex`, `k_ReleaseSemaphore`, the definition of `hle_dbg_missed_wakes`), `third_party/pcrecomp/runtime/win32hle/kernel32_crt.c` (`thread_trampoline` sets `done` and wakes under the machine; `k_ExitThread` wakes before `hle_block_begin`), `third_party/pcrecomp/runtime/win32hle/win32hle.h` (`hle_wake`, `hle_dbg_missed_wakes`), `third_party/pcrecomp.PATCHES`, `runtime/bw2/perf.c` (Task 1's weak `hle_dbg_missed_wakes` is removed; the exit line reads the real one), `tests/test_boot.py` (`LOUD` gains `"missed wake"`).
- Test: `tests/test_engine.py`.

**Interfaces:**
- Consumes: Task 1's exit line (`polls`, `missed wakes`) for the tests.
- Produces:
  - `void hle_wake(void)` (win32hle.h): called **while holding the machine** after any change that can make `try_take` answer 1. It locks a host mutex `g_wake_mu`, and if the sleeper count `g_sleepers` is not 0 bumps the wake generation `g_wake_gen` and `pthread_cond_broadcast`s `g_wake_cv`; then unlocks. (One uncontended lock and a compare when nobody sleeps.)
  - **The protocol (no lost wake).** A waiter, still holding the machine and after its last `try_take` found nothing ready, locks `g_wake_mu`, does `g_sleepers++`, reads `gen = g_wake_gen` and unlocks; only then `hle_block_begin`. It then locks `g_wake_mu` and `pthread_cond_timedwait`s while `g_wake_gen == gen` and neither its deadline nor the backstop has passed, does `g_sleepers--`, unlocks, `hle_block_end` and checks again. Because every signaller holds the machine when it calls `hle_wake`, a signal either comes before the waiter's last check (the check sees it) or after its generation read (the generation changes). A host thread that signals a guest object must take the machine first (`mach_enter`, as winmm's timer threads do). The one signal raised outside the machine today, a thread's end, moves under it: `thread_trampoline` does `mach_enter(); a->done = 1; hle_wake(); mach_leave();` after `hle_call_guest` returns, and `k_ExitThread` calls `hle_wake()` after setting `done` and before `hle_block_begin`.
  - `hle_wait(int n, const uint32_t *h, int all, uint32_t timeout)` keeps its signature and answers. When nothing is ready and the timeout is not 0 it sleeps as above until the generation changes, the timeout's deadline passes, or `HLE_WAIT_BACKSTOP_MS` (100) passes, and checks again. A zero timeout checks once and returns, never sleeping.
  - **`all` waits take all or nothing.** `try_take(h, peek)`: with `peek` set it answers whether the object is ready (an event signalled, a semaphore above 0, a mutex free or owned by this thread, a thread ended) without changing it. The `all` branch first peeks every handle; only when every one is ready does it take every one (no other guest thread can run in between: the caller holds the machine). This replaces today's take-as-it-checks (`kernel32.c:452-454`), which consumed an auto-reset event's signal while the semaphore was still 0 and then never saw the event again. An invalid handle still answers `WAIT_FAILED`.
  - **The backstop names a missed wake.** When a wait woke by the backstop with no generation change and `try_take` then answers 1, `hle_dbg_missed_wakes++` and, the first time for that handle type, `[win32hle] missed wake: handle 0x%08X (type %d) was ready with no hle_wake` is printed. The game goes on (the wait is answered); every boot test fails on the line (`LOUD`).
  - `hle_enter_cs` waits the same way when the section is owned by another thread (no `usleep(50)` loop; its owner check runs under the machine after `hle_block_end`, a call, so it always rereads guest memory); `hle_leave_cs` calls `hle_wake` when it frees a section and a thread is waiting in `hle_enter_cs` (a host count, `g_cs_sleepers`).
  - `extern volatile unsigned hle_dbg_missed_wakes;` (win32hle.h), defined in `kernel32.c` (the only definition; `perf.c`'s weak one goes).
  - `ResetEvent` and `PulseEvent` keep their behaviour (they only clear).

## Rulings (my calls; the spec leaves them to the builder)

1. **Scope and number.** Plan 6 is done, so this is plan 14. The boot has no unanswered layer, the app is built by the Builder (plan 13), and the user's order (2026-11-14) puts performance next. This plan takes the three costs the spike measured in the land and the tools to measure them; each of its five tasks is a review gate.
2. **The bench lives in `tools/`, not in the default suite,** and refuses to measure on a busy Mac (the user's rule 2, built into the tool so no agent can forget it). It reuses the boot tests' scripts through `sys.path` rather than moving them, so no boot test changes. It measures headless at the game's default 1024x768; its numbers compare our layers before and after, not the user's experience.
3. **Waits sleep on one condition variable with a 100 ms backstop.** One generation counter and broadcast keeps the change small and inside win32hle (where the polling lives); waking every sleeper on every signal is cheap with four or five guest threads. It is race-free only because signallers and the waiter's registration both happen under the machine (Task 2's protocol). The backstop keeps a forgotten wake from hanging the game forever, and naming it (`missed wake`, a `LOUD` line in the tests) keeps it from being silent.
4. **No `restrict` base pointer in this plan.** Spec 7.1 asks for the memory base as a separate `restrict` value so clang knows guest accesses do not alias host state; plan 1 made the base a compile-time constant (`RECOMP_MEM_BASE`, spec 5.2), so there is no pointer to mark. clang may still reload host globals the lifted code keeps in memory (`g_st`, `g_xmm`, `g_fp_top`) after a guest store; whether that costs enough to matter is for Task 4's profile to show and a later plan to take, not this one. Dropping `volatile` is safe because guest threads run one at a time under the machine lock and change hands only through calls ("Measured" item 8); `-fno-strict-aliasing` stays.
5. **Commit at pass boundaries, not inside passes.** Apple GPUs keep a pass's targets in tile memory; splitting a pass would add a load and a store of every target. The frame already has 22 passes, so ending a command buffer where a pass ends costs nothing extra. 64 draws keeps tiny passes (a clear, one quad) together. The commit is made at a chunk point at the start of a draw or Clear (after the targets are applied, before any serial is read), not inside `mtl_draw`: by then the draw has already marked its buffers and heap copies with the old buffer's serial.
6. **Native resolution in a window is measured by the user.** An agent's window would appear on the user's screen while they work, and the scripted clicks are pinned at 1024x768 (`saves.md`). The meter works in the app too (`BW2_PERF=1` in the app's environment writes the lines to `Logs/bw2.log`), so the user's own runs can give those numbers.
7. **What this plan leaves alone:** the game's own `Sleep(0)` spin (it is the game's code, and it ends sooner once the GPU has its work earlier), the PSO and sampler caches keyed by `NSData` and the O(1) dispatch hash (each under 3% in the spike's profile, which was taken under load and only points where to look), and the slowdown after long play noted in `campaign.md` (510 s and more: the user's long sessions will show whether it remains).
