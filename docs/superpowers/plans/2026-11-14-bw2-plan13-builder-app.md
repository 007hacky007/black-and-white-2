# Plan 13: The Builder app and packaging Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The user turns their own disc images and the three patches into `Black & White 2.app` with a small native Builder app and no Terminal (spec sections 2 and 8): a checklist of rows, a Build button, a Play button. The app is self-contained, ad-hoc signed, opens from Finder, and ships nothing from Homebrew.

**Architecture:**
- **No Homebrew in the build.** Today the pipeline calls Homebrew's `unshield` and `innoextract` from `PATH` and links Homebrew's GPL FFmpeg (plan 10 Ruling 2). A user's Mac has none of these. The fan patch's `white.exe` is taken out of its Inno Setup installer in Python (Task 1); unshield 1.6.2 (MIT) is vendored as source and compiled by the pipeline with the Command Line Tools' clang (Task 2); an LGPL-only FFmpeg is built from the pinned 9.0.2 tarball with only the Bink demuxer and decoders, as plan 10 Ruling 2 decided (Task 3).
- **The engine is the app's executable.** There is no launcher process: `Contents/MacOS/bw2` finds its game and the lifted DLL inside the bundle when started with no arguments, writes its output to a log in the support folder, and a small watcher (the same binary, spawned at start) shows an alert when a run ends in a loud stop (Task 4). `bw2.app` assembles the bundle: the game tree APFS-cloned and checked against its manifest, the d3dx DLL in `Resources` (it breaks signing in `MacOS`, "Measured" item 2), FFmpeg in `Frameworks`, ad-hoc signed and verified (Task 5).
- **One command, then one window.** `python -m bw2.builder_cli build` takes the inputs and runs every step with `BW2-EVENT` lines (Task 6). The Swift Builder, adapted from the user's own NFSU2 Builder (spec section 2's one exception), installs a pinned Python, runs that command in its own process group, and shows the rows (Tasks 7 and 8). `python -m bw2.make_builder` makes `BW2 Builder.app` with the git-tracked sources inside it.
- **Next layer:** performance (the user's order, 2026-11-14), then gameplay bugs from the user's reports.

**Tech Stack:** Python 3.14 (pytest; `lzma`, `zipfile`, `plistlib`, `http.cookiejar`), C (clang, arm64, macOS 13+), unshield 1.6.2 source (MIT), FFmpeg 9.0.2 source (LGPL-2.1+, built on the user's Mac, never in the repo), python-build-standalone CPython 3.14.10, Swift 5.9 package (SwiftUI, XCTest, CryptoKit), `codesign`, `xattr`.

**Spec:** `docs/superpowers/specs/2026-11-10-bw2-macos-port-design.md` (sections 2, 3, 5, 7.5, 8, 9, 11). Facts: `docs/research/install-tree.md`, `official-patches.md`, `patch-application.md`, `build-pipeline.md`, `campaign.md` (FFmpeg), `land1.md`.

After the magic: one LZMA2 dictionary-size byte, then a raw LZMA2 stream; Python's `lzma` (`FORMAT_RAW`, `FILTER_LZMA2`) decoded it in 0.72 s to 38,054,164 bytes, stream ended, 1,109,041 bytes after it. As stored its SHA-256 is `c73141fd7678d0659fab9f5648bd5253ea6223cea492e98e52123857fe103144`; after Inno's call-instruction transform is undone it is `ca745211...db2`, the `white-exe` release (1.25 s in pure Python). The transform (decode direction), per 64 KiB block of the file's data, with `i` counted from the block's start and `base` the block's offset in the file:
   ```
   i = 0
   while i < block_size - 4:
       if b[i] in (0xE8, 0xE9):
           i += 1
           if b[i+3] in (0x00, 0xFF):
               addr = (base + i + 4) & 0xFFFFFF
               rel = (b[i] | b[i+1] << 8 | b[i+2] << 16) - addr
               if rel & 0x800000: b[i+3] ^= 0xFF
               b[i:i+3] = (rel & 0xFFFFFF).to_bytes(3, "little")
           i += 4
       else:
           i += 1
   ```
   An instruction whose operand would cross the block's end is left alone (the `block_size - 4` bound); the 4-byte skip applies whether or not the high byte qualified.

## Rulings (my calls; the spec leaves them to the builder)

1. **Scope and number.** Plan 6 is done, so this is plan 13. The boot reaches the front end with no stop of its own and scripted runs play into the first land (plan 12); the user's order after plan 12 (2026-11-14, spec 11) is the Builder app and packaging, then performance. Both are one plan because the Builder is only useful once every step it runs works without Homebrew, and each of the eight tasks is its own review gate.
2. **The fan patch is read in Python, not with innoextract.** innoextract (zlib licence) needs Boost and CMake to build, which a user's Mac lacks. The installer is pinned by SHA-256, so its fixed offsets are facts about a known file, and the output is checked against the pinned `white.exe`; a different installer fails by name before any offset is used. The transform is written from its measured behaviour ("Measured" item 3), not copied.
3. **unshield is vendored as source (MIT, 1.6.2, byte-identical) and built by the pipeline with clang.** No open Python reader handles InstallShield 9 volume spanning (phase 0), and Homebrew is not on a user's Mac. Our config header replaces CMake; MD5 comes from CommonCrypto through a small `openssl/evp.h` of ours, so neither OpenSSL nor the RSA reference MD5 (a different licence) is needed. It is not part of pcrecomp, so no `PATCHES` line.
4. **FFmpeg as plan 10 Ruling 2 decided,** with the exact configure flags of Task 3: only the Bink demuxer and the three Bink decoders, `--disable-autodetect` (no VideoToolbox or other system links), `@rpath` install names, built once per workspace from the pinned tarball and kept by `clean`. Development keeps Homebrew's build; `package_app` refuses an engine linked to it.
5. **Python:** python-build-standalone `20261026`, CPython 3.14.10 (the series the repo is developed on), pinned by SHA-256; the three wheels are installed with `--require-hashes --only-binary=:all:`, so no compiler runs for them. pytest is not a Builder requirement.
6. **No launcher process.** The engine is `CFBundleExecutable`, so LaunchServices, the Dock and AppKit see one process (spec 7.5's launcher clause does not apply). Loud ends cannot be caught at one place in the engine (about 90 exit sites), so a watcher (the same binary, spawned at start, never touching AppKit) reads the output and decides from the last engine line; the user sees an alert and a log, never a silent vanish. The d3dx DLL lives in `Resources` because `codesign` refuses it in `MacOS` ("Measured" item 2). No icon in this plan: the game's own icon is in `white.exe` and could be converted on the user's Mac later.
7. **Identifiers:** `local.bw2-port.game` and `local.bw2-port.builder`, no personal or real domain; version `0.1.0` in `VERSION`.
8. **Downloads go through the Python CLI,** so one tested implementation serves the Builder and the developer. The PCGamingWiki rows say that downloading accepts that site's download terms for the user, as `official-patches.md` asked.
9. **Disc rows are fast:** a zip is identified by its central directory (bin name, size, CRC-32), so the row turns green without unpacking 3 GB; the full SHA-256 of each bin is still checked in the build's `discs` step. Bins and ISOs are hashed in the row (CryptoKit, in the background). The ISO fingerprints are computed from the redump bins ("Measured" item 8); an ISO from a tool that differs is "not a known disc" and the row says so.
10. **The workspace is cleaned after a successful install** (`gamefiles/`, `gen/`, `out/` except `out/tools/`): the app holds everything it needs, and the build tree is about 10 GB. A rebuild starts again from the inputs. Saves and settings live outside both and are never touched.
11. **Destination:** `/Applications`, else `~/Applications`; replacing an app is refused while it runs, and the old one is restored if the move fails.
12. **The end-to-end builds are not play sessions.** They run the build and at most a 300-read front-end boot; they carry the `builder_e2e` marker (opt-in, `BW2_BUILDER_E2E=1`, about 15 to 25 minutes) because they take longer than the default suite should grow. Each is run once in its task; their times are recorded, never asserted.
13. **No new Homebrew package.** The Builder and the app need only the Command Line Tools; Xcode is needed only by the developer who makes `BW2 Builder.app` (`swift build`, XCTest).
14. **The window is checked through its calls, not by clicking.** Agents have no reliable way to drive a SwiftUI window here, so the logic lives in `BuilderCore` (unit-tested), `--print-checks` shows the rows headless, and `EndToEndTests` makes the window's calls in the window's order. The user's first real use of the window is the acceptance check.
